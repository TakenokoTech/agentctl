# 意思決定

## いつ使うか

- 使う: 構成、層、依存、パッケージの配置、公開インターフェース(CLI、MCP のツール)、互換性、外部サービスの選定など、あとから変えると差分が大きいもの。
- 使わない: バグ修正、小さなリファクタリング、文言の変更、既存の規約どおりの追加。

## 手順

1. **論点を洗い出す。** 決めることを軸ごとに列挙する: 何を作るか / どう実現するか(方式) / どこに置くか(配置) / 範囲。暗黙の前提(「`crates/` を作る」など)を書き出し、決まっていないものはユーザーに尋ねる。「何を」だけを聞いて実装に入らない。
2. **先行事例を調べる(案を出す前に)。** 実在のリポジトリやドキュメントを確認し、件数と出典を書く。読んでいない部分は、推測と明記する。
3. **案を3〜5つ出す。** 評価軸と重みを決め、点数を表にし、重みを変えたときの順位(感度)も示す。点数は、実測に基づくものと主観を分けて書く。
4. **実測できるものは試す。** リポジトリを触らず、コピー上で試作する(テスト件数、バイナリの大きさ、手順の数など)。
5. **推奨を書く。** 点数に入っていない判断があれば明示する。結論を書く前に、生成した表と取得した事実に突き合わせる。
6. **ユーザーに選んでもらう。** 選択式の UI で尋ねる。
7. **決定を ADR に記録する。** `docs/adr/template.md` を使う。検討のメモは `.temp/` に置いてよいが、残すものは ADR に要約する(`.temp/` はコミットされない)。
8. **ルールとコードがずれたら、どちらを直すかを先に決める。** ルールの文書を実態に合わせて緩める前に、コードをルールに合わせられないか、ルール自体が古いのかを確認する。

## ADR の扱い

- 置き場所は `docs/adr/`、ファイル名は `NNNN-タイトル.md`(連番)。日本語で書く。
- ステータスは `Proposed` / `Accepted` / `Superseded by NNNN`。`Accepted` にした ADR は書き換えない。決定を変えるときは新しい ADR を作り、古い方を `Superseded by` にする。
- まだ決まっていない論点も、`Proposed` の ADR として残してよい。
