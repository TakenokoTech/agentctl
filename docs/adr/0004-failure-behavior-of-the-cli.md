# 0004. 失敗時の挙動(タイムアウト、watch の終了、起動失敗の診断)

- ステータス: Accepted
- 日付: 2026-11-08
- 関連: ADR 0001(MCP ラッパーの方式)

## 状況

`/code-review` の指摘のうち、修正方法が一つに決まらない4件(TODO 16・18・20・21)の判断。いずれも、失敗したときの CLI の挙動で、スクリプトや AI エージェントから見える仕様になる。

- 応答しない A2A / MCP サーバーを相手にすると、CLI が止まり続ける。
- `a2a task watch` は、タスクが終端状態に達する前にストリームが閉じても終了コード 0 になり、成功と区別できない。サーバーが終端状態のあともストリームを閉じないと、戻らない。
- stdio の MCP サーバーの標準エラーを捨てているため、起動に失敗した原因が見えない。

## 決定

| 論点 | 決定 |
|---|---|
| タイムアウト | 既定値 60 秒。`--timeout <秒>`(環境変数 `AGENTCTL_TIMEOUT`)で変更でき、`0` は制限なし。超過は終了コード 1 と `timed out after Ns … (change it with --timeout)`。`a2a task watch` は全体の制限から除く(接続の制限は掛ける) |
| watch が途中で閉じた | 終端状態に達する前にストリームが閉じたら、終了コード 1 と `stream closed before the task finished (last state: …)`。届いたイベントは出力する |
| watch の停止 | 終端状態(`completed` / `failed` / `canceled` / `rejected`)を受けたら、ストリームが閉じるのを待たずに終わる。終了コードはその状態に従う(`failed` と `rejected` は 2、`canceled` は 0) |
| stdio サーバーの起動失敗 | 接続に失敗したときだけ、サーバーの標準エラーの末尾(20行、1行 500 文字まで)をエラーに含める。通常は捨て続ける |

## 検討した案

点数化していない(各論点について、選択肢と推奨を示し、ユーザーが選んだ)。

| 論点 | 採用 | 退けた案 |
|---|---|---|
| タイムアウト | 既定値つき + `--timeout` | 設定ファイルでサーバーごとに指定(指定しないと無制限のまま)、対応しない(呼び出し側に任せる) |
| watch が途中で閉じた | 終了コード 1。`canceled` は成功のまま | 1 にして `canceled` も 2 にする(`task cancel` の成功が 2 になり、コマンドの成否と組み合わせにくい)、現状維持 |
| watch の停止 | 終端状態で終わる | 終端状態のあと短い猶予を置く(待ち時間とテストの複雑さが増える)、現状維持(サーバーの実装に依存する) |
| 起動失敗 | 失敗時だけ標準エラーの末尾を含める | `--server-stderr` オプションで常に通す(失敗してから再実行が必要)、現状維持 |

## 結果

- 良い点: 応答しないサーバーで止まらない。`watch` の終了コードで、タスクが終わったかを判別できる。起動に失敗した MCP サーバーの原因が、エラーメッセージで分かる。通常の出力に、サーバーのログは混ざらない。
- 代償:
  - 既定の 60 秒を超える正当な呼び出しは、`--timeout` で延ばす必要がある。
  - `task watch` は、最初のリクエストの応答が来ないケースを、制限時間では止められない(接続の制限は効く)。
  - 終端状態の直後に流れるイベント(最後の artifact など)は、受け取らずに終わることがある。
  - 標準エラーを常に読み続けるため、stdio サーバーごとに読み取りのタスクが1つ増える。
- 見直す条件: 正当な呼び出しが 60 秒を超えるケースが多いとき(既定値の見直し、またはサーバーごとの設定)。終端状態のあとのイベントを取りこぼして困るとき(猶予の導入)。
