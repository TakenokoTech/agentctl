# 0001. MCP クライアントから agentctl を使う方式

- ステータス: Accepted
- 日付: 2026-11-08
- 関連: ADR 0002(配置)、ADR 0003(内部構成)

## 状況

`agentctl` を、MCP クライアントから(シェルを介さずに)使えるようにする。デザインまとめで「案B(1つのコアを CLI / MCP サーバー / A2A サーバーの入口で公開)」として、当初は選ばなかった構成にあたる。

最初に「`agentctl` のコマンドを MCP ツールとして公開する」とだけ決め、実現の方式は確認しなかった。そのため、同じバイナリの `agentctl serve` として、アプリケーション層を直接呼ぶ形を実装した。その後、「MCP サーバーが CLI を呼ぶ形で、コードベースが一緒になっていないか」と指摘を受け、方式を検討し直して、この実装は取り下げた。

## 決定

別のプログラム `agentctl-mcp` が、ツール呼び出しのたびに `agentctl` をサブプロセスで実行し、標準出力と終了コードを MCP の結果にする。

- 公開するツールは8つ: `list`、`mcp_tools`、`mcp_schema`、`mcp_call`、`a2a_card`、`a2a_send`、`a2a_task_get`、`a2a_task_cancel`。ストリームを返す `a2a task watch` は、ツール呼び出しが1回の応答で返るため公開しない(`a2a_task_get` で確認する)。
- トランスポートは stdio のみ。Streamable HTTP は対象外。
- 終了コードが 0 以外なら `isError`。終了コード 2 は標準出力(tool や task の内容)、1 は標準エラー(`error: …`)を本文にする。
- 呼び出し側(LLM など)が与える値が、`agentctl` のオプションとして解釈されないようにする。名前と ID は `-` で始まるものを拒否し、自由なテキストは `--` の後ろに置く。`mcp_call` の引数は標準入力で渡す。

## 検討した案

| 案 | 概要 | 評価 |
|---|---|---|
| 同じバイナリの `agentctl serve` | アプリケーション層を直接呼ぶ | 実装したが取り下げた。ドメインの `trait` に `Send` を付ける変更が必要で、CLI と MCP のコードベースが一体になる |
| **別プログラムが CLI を呼ぶ** | サブプロセスで `agentctl` を実行する | **採用** |
| 設定済みの MCP サーバーを束ねるプロキシ | 各サーバーのツールを1つの MCP から見せる | ツール定義が全部コンテキストに載り、段階的に開示する設計と反する |
| 任意のシェルコマンドを実行するツール | 任意のコマンド実行を MCP 経由で許す | 設定済みの対象に限る方針と合わない。安全性のリスクが大きい |

この決定は、点数化していない(上の選択肢から、ユーザーが選んだ)。

## 結果

- 良い点: `agentctl` の CLI が唯一の入口のまま保たれる。出力と終了コードが CLI と一致する。`agentctl` 本体のコードを変更しない。オプション注入を、入力の検証で防げる。
- 代償: ツール呼び出しのたびにプロセスを起動する。CLI の出力形式に依存する(ずれは、本物の CLI と結合する E2E で検出する)。
- 先行事例との違い: 調べた9件(ADR 0002 を参照)はいずれも、MCP と CLI がコードをプロセス内で共有していた。サブプロセスで同梱の CLI を呼ぶ例は、調べた範囲では見つからなかった。
- 見直す条件: 呼び出しの遅延が問題になったとき。または、CLI の文法が頻繁に変わり、ずれが実害になったとき。その場合は、共有コアの切り出し(ADR 0002 の P5、ADR 0003 の E)を検討する。
